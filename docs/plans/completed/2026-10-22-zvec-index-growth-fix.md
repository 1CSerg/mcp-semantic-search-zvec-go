# Устранение избыточного роста zvec-индекса — план реализации

> **Для исполнителя:** использовать `subagent-driven-development` либо `executing-plans`, выполнять задачи с проверкой результатов. Реализация этим документом не разрешается.

**Статус:** **реализован и проверен 22 октября 2026 года.** См. разделы [Результаты реализации](#результаты-реализации) и [Замеры до и после](#замеры-до-и-после) в конце документа. Все задачи 1–6 выполнены; коммиты не создавались — пользователь их не разрешал.

**Цель:** ограничить накопление файлов векторных блоков при индексации, сохранив durability, согласованность манифеста и работоспособность поиска.

**Архитектура:** периодическая компакция по числу операций записи плюс финальная компакция dirty-коллекции. Сохранить flush перед обновлением манифеста и текущую сериализацию доступа к native handle. Компакция — best-effort обслуживание, а не условие успешности записи.

**Стек:** Go, CGO, zvec-go v0.7.0, native zvec, SQLite manifest; существующие build tags и режимы active/staging.

**Основание:** запрос пользователя проверить применимость проблемы из [описания другого проекта](zvec-index-growth.md); результаты проверки ниже. План согласован для сохранения, не для исполнения.

## 1. Результаты проверки

**Проблема применима к этому проекту на уровне кода. Фактическое раздувание рабочего индекса этого проекта пока не измерено.**

Подтверждённые факты:

- [go.mod](../../../go.mod) требует zvec-go v0.7.0; локальный checkout действительно имеет тег v0.7.0 и native submodule pin `8321c1314a559fd5f909e92498f43e5194bf9b99` — тот же, что в исходном описании.
- [UpsertChunks](../../../internal/store/zvec/collection.go) вызывает `Flush()` после каждого upsert (на момент проверки строки 186–203). [Coordinator](../../../internal/indexer/coordinator.go) выполняет upsert для каждого embedding-batch (582–604): большой файл создаёт несколько блоков.
- `DeleteByIDs` также вызывает `Flush()` после удаления (220–244). Не каждый delete-only flush обязательно создаёт векторный блок: это зависит от наличия memory-компонентов.
- В приложении нет вызовов `Optimize()`; [Store](../../../internal/store/zvec/store.go) не предоставляет обслуживание индекса. В [локальном биндинге](../../../.deps/zvec-go/collection.go) нужный метод уже есть (220–224).
- В upstream на точном пине [SegmentImpl::flush](https://github.com/alibaba/zvec/blob/8321c1314a559fd5f909e92498f43e5194bf9b99/src/db/index/segment/segment.cc) завершает memory-компоненты и выделяет следующий блок. [CollectionImpl](https://github.com/alibaba/zvec/blob/8321c1314a559fd5f909e92498f43e5194bf9b99/src/db/collection.cc) содержит явную компакцию; штатное закрытие выполняет flush, а не optimize.
- Flush предшествует обновлению манифеста в Coordinator (631–649). Удалять или откладывать его в рамках исправления нельзя.
- Соседний дефект также присутствует: `DeleteByIDs` возвращает ошибку при любом `ErrorCount > 0`, а [cleanup journal](../../../internal/indexer/coordinator_helpers.go) может повторно удалять уже отсутствующие ID.

**Ограничения проверки:** MCP `index_status` / `semantic_search` недоступны. Native-воспроизведение и тесты не запускались. В checkout индекс не найден. Обнаруженная user-level коллекция `ws_f2cf5382ce15c6e0` занимает 5 284 082 байта, содержит один `.proxima` размером 5 271 552 байта; её принадлежность этому проекту не установлена, поэтому это не замер рабочего индекса проекта. Рабочие коллекции не открывались и не изменялись.

При проверке в основном репозитории уже были пользовательские изменения и планы обновления; в зависимости — ACP-патч и дополнительные файлы. Сохранить их нетронутыми.

## 2. Выбранный подход и глобальные ограничения

Добавить **периодическую компакцию по числу операций записи плюс финальную компакцию только при наличии изменений**.

Почему не альтернативы:

- Уменьшение частоты flush затрагивает crash-consistency и требует отдельного проектирования транзакций.
- Только финальная компакция не ограничивает пик дискового пространства во время большого прогона.
- Optimize после каждой записи слишком дорог: многократная перестройка растущего индекса создаёт квадратичную нагрузку.

Ограничения:

- Сохранить схему FP32/HNSW, dimensions, идентичность коллекций, MCP/HTTP API и конфигурацию.
- Не объединять исправление с [планом обновления до v0.8.0](../2026-10-21-zvec-go-v0.8.0-upgrade.md); если обновление будет выполнено раньше, повторить native-проверку на новом комплекте.
- Не трогать существующие пользовательские изменения и рабочие коллекции.
- Сохранить текущую модель сериализации через mutex хранилища. Компакция временно задержит поиск/запись этой коллекции; не освобождать mutex вокруг native handle без отдельного решения его lifetime.
- Не добавлять фоновые goroutine, таймеры или новые настройки в первой версии.
- Не удалять `.proxima` вручную. Ошибка обслуживания не должна маскировать ошибку записи или flush.

## Основные риски для ревью

1. No-change, пустая или отсутствующая коллекция: не создавать коллекцию и не вызывать native optimize без dirty-состояния; тесты задачи 2.
2. Частичный успех записи, неоднозначный flush и rollback: не потерять dirty-состояние и исходную ошибку; тесты задач 2–3.
3. Force staging и Windows rename: обслуживать staging до закрытия и promote, не публиковать незавершённый индекс; тесты задачи 3.
4. Отмена, Close и одновременный поиск: не начинать новую дорогую работу после отмены, не допускать use-after-close и deadlock; задачи 2, 3, 5.
5. Повторное удаление, смесь отсутствующих/существующих ID и повторы ID: идемпотентность без ложного успеха при Fetch/flush error; тесты задачи 4.

## Критерии завершения

Рост блоков воспроизведён и устранён на временной коллекции; unchanged-прогоны не выполняют optimize; durability и staging-публикация сохранены; ошибки обслуживания не срывают индексацию; повторное удаление не зацикливает cleanup. Новые публичные API, настройки и изменения схемы хранения не требуются.

## Самопроверка плана

- Причина роста и соседняя ошибка удаления разделены; факты исходников отделены от ещё не выполненных runtime-проверок.
- Порог считается по операциям, а не файлам; промежуточные ошибки не вызывают optimize на каждом следующем batch.
- Optional Compactor не ломает существующие Store/mocks; `compactLocked` не захватывает тот же mutex повторно.
- Финализация staging идёт до close/promote; отмена не запускает новую дорогую работу; no-op определяется dirty-флагом.
- Историческое раздувание требует отдельного согласованного восстановления; рабочие данные не изменяются самим исследованием или сохранением плана.

### Замеры до и после

Native-комплект этого checkout: Windows amd64, `zvec_c_api.dll` из
`.deps/zvec-go/lib/windows_amd64`. Fixture: 256 батчей x 4 документа (1024 документа,
dimensions 8), детерминированные векторы, один `Flush()` на батч — ровно то, что делает
`CollectionStore.UpsertChunks`.

| Состояние | файлов `.proxima` | байт `.proxima` | весь каталог коллекции |
|-----------|------------------|-----------------|------------------------|
| Без обслуживания (256 flush) | 256 | 1 349 517 312 | 1 350 646 011 |
| После одного native `Optimize()` | 1 | 4 182 016 | 5 274 658 |
| Store с политикой компакции | 1 | 5 226 496 | 5 952 783 |

Каждый flush выделял блок ровно 5 271 552 байта независимо от числа документов, поэтому
1024 документа занимали 1,35 ГБ. Политика сокращает `.proxima` в 256 раз по числу
файлов и в 258 раз по байтам (требование плана — минимум в 4 раза).

Прочие измерения: прогон 256 батчей с политикой — 4,17 с; пиковый размер каталога
(замер каждые 32 батча) — 512 283 371 байт; один `Optimize()` — 79,75 мс; максимальная
задержка поиска во время него — 96,6 мс. `scalar.N.parquet` (~2,7 КБ x 512) также
накапливаются, но `Optimize()` их не освобождает — это ~1,4 МБ, вне области плана.

Бюджет вызовов native optimize: unchanged-прогон — 0 вызовов; 200 батчей — ровно 1
периодический (200/128) + 1 финальный; после чистого финала — 0.

### Принятые решения при реализации

Зафиксированы, поскольку расходятся с буквальным текстом плана либо уточняют его.

1. **Unit-тесты политики не используют native collection.** `compaction_test.go`
   проверяет `writeOutcomeLocked` и `compactLocked` — ровно те функции, которые
   вызывают оба write-пути, — потому что native `*zvec.Collection` нельзя подменить без
   переделки всего native API, что план запрещает. Сквозная связка
   (`UpsertChunks` не возвращает ошибку при сбое `Optimize`, реальная коллекция
   остаётся dirty) покрыта native-тестом
   `TestCompactionOptimizeFailureDoesNotFailWrite`. Важное следствие: связка
   «write-путь вызывает `writeOutcomeLocked`» проверяется **только** в сборке
   `integration,zvec` — в unit-сборке `-tags zvec` набор политики остаётся зелёным,
   даже если вызов из `UpsertChunks`/`DeleteByIDs` пропадёт. CI гоняет
   `zvec-integration`, поэтому дыры в покрытии нет, но полагаться на unit-прогон здесь
   нельзя.
2. **`Close` сохраняет `dirty`/`writeOps`.** Они описывают on-disk коллекцию, а не
   handle; переоткрытие продолжает обслуживание с того же места. `WipeCollection`
   сбрасывает счётчики, потому что коллекция исчезает.
3. **`promoteStaging` теперь всегда закрывает staging-store до вызова тестового хука**
   `forcePromoteStaging` (раньше ветка хука его не закрывала, а `defer` закрывал после).
   Флаг `stagingClosed` защищает от двойного закрытия. Это делает наблюдаемый порядок
   `compact → close → promote` одинаковым для хука и реального пути.
4. **На force-пути `finalizeTarget = nil`.** Иначе каждый force reindex перестраивал бы
   активную коллекцию, которую вот-вот заменит. Staging обслуживается в
   `promoteStaging`, то есть до `Close` и promote; неуспешный staging не обслуживается
   вовсе.
5. **Отменённый прогон не запускает финальную компакцию** (проверка `ctx.Err()` в
   `compactStoreBestEffort`), а упавший прогон с живым контекстом — запускает, чтобы
   частичные изменения были утилизированы. Исходная ошибка прогона при этом не
   подменяется.
6. **Задача 4 не потребовала изменений в координаторе.** Дефект целиком внутри
   `DeleteByIDs`; `reconcileCleanupJournal` очищает журнал сразу после успешного
   удаления, поэтому повторный replay становится no-op бесплатно. Повторное удаление
   покрыто на уровне, который владеет контрактом, —
   `TestIntegrationDeleteIsIdempotent` (двойное удаление + переоткрытие).
7. **`deleteError` при сбое пост-delete `Fetch`** возвращает `PartialWriteError` с
   `Succeeded: nil` и `Failed: len(requested)`: план запрещает и выдавать сбой Fetch за
   успех, и выдумывать per-ID результаты.
8. **Порог 128** — начальный компромисс, не гарантия постоянного размера или времени.
   При неприемлемой задержке политику нужно менять согласованно, а не ослаблять
   критерии.
9. **Обслуживание пропускается на read-only handle.** Найдено на финальном ревью:
   force reindex, удаляющий исчезнувший файл, оставляет dirty-флаг на активной
   коллекции; `promoteStaging` затем переоткрывает её read-only, и на следующем
   unchanged-прогоне `Optimize()` на read-only handle не может выполниться — предупреждение
   в каждом запуске и вечно не сбрасываемый флаг. `compactLocked` теперь возвращает
   no-op при `s.readOnly`, сохраняя dirty до записи-способной сессии.

### Итоги внешнего ревью (22 октября 2026)

Два независимых ревьюера с чистым контекстом отработали полный диф. Critical не
найдено ни одним. Исправлено по итогам:

1. **`FlushWriteError` трактовался как завершённое удаление.** `DeleteByIDs` возвращает
   `FlushWriteError` со всем `requested` в `Succeeded`, а `deleteStaleVectorsFrom`
   через `PartialWriteOutcome` вычитал эти ID из набора повторов и возвращал успех:
   файл помечался проиндексированным, хотя удаление не стало durable, а цикл повторов
   (3 попытки) обходился. Теперь набор повторов сокращает только `PartialWriteError`
   (`errors.As`), где `Succeeded` — проверенный результат; `FlushWriteError` повторяется.
   `TestDeleteStaleVectorsFlushFailureIsRetriedNotSucceeded` RED→GREEN.
2. **На force-пути терялись изменения active от replay cleanup journal.** Журнал
   воспроизводится в активную коллекцию до выбора staging; при успешном promote она
   заменяется (обслуживать её бессмысленно), но при **неуспешном** force-прогоне она
   продолжает обслуживать запросы, а `dirty` жил только в памяти и терялся с процессом.
   Добавлен флаг `promoted`: `finalize()` обслуживает активную коллекцию только если
   staging был выбран и не был опубликован.
   `TestCoordinatorFailedForceReindexStillCompactsActiveJournalChanges` и
   `TestCoordinatorSuccessfulForceReindexDoesNotCompactActive` RED→GREEN.
3. **Тест staging не мог упасть.** Fixture писал 256 батчей = 2 × порог, поэтому
   периодическая компакция уже отрабатывала внутри `UpsertChunks`, а явный `Compact()`,
   который тест якобы проверял, был no-op. Fixture уменьшен до 64 батчей (ниже порога),
   добавлены абсолютные проверки: 64 блока → ≤2 после `Compact()`.
4. **Тесты координатора проверяли «фейк вызван», а не «работа была».** У фейка появился
   `dirty`-флаг (как у `CollectionStore`), событие несёт `dirty=`, положительные
   проверки требуют `dirty=true`. Тест «упавший прогон с частичными изменениями» теперь
   действительно пишет первый файл (`failAfter: 2`, второй файл), иначе утверждение в
   имени теста было ложью.

Прочее исправлено: дублирование имени операции в тексте `PartialWriteError`; nil-guard
в тестовом хуке `countingOptimizer` (хук вызывается при удержанном `mu`); утечка native
handle в baseline-fixture при `t.Fatalf`; усилена проверка «dirty переживает no-handle
pass».

Также исправлено по minor-замечаниям: один defer закрытия staging вместо двух (теперь
регистрируется до присваивания `stagingStore`, поэтому покрывает и ошибку
`manifest.Open`); `dedupeIDs` без map на одном ID (горячий путь rollback-удалений);
`remainingIDsLocked` запрашивает только `name` вместо всех полей; удалена недостижимая
ветка после `dedupeIDs`.

Отклонено с обоснованием:

- **Убрать периодическую компакцию из write-пути** (аргумент: `Optimize()` под `s.mu`
  блокирует `Search` на всё время перестройки). Это прямо противоречит плану, который
  требует «периодическую компакцию по числу операций записи» и «сохранить текущую модель
  сериализации через mutex хранилища». Замеры: `Optimize()` на fixture — 79,75 мс,
  максимальная задержка поиска во время него — 96,6 мс. Для больших индексов задержка
  растёт, и это зафиксировано в документации как известная цена; вынос в фон — отдельное
  проектное решение, а не правка этого плана.
- **Guard на «мёртвый» native handle в `optimizeLocked`.** Предложено проверять `s.open`,
  но это состояние им не отличается: при ошибке `Close` оба поля (`s.col`, `s.open`)
  остаются как были, а сама схема «вызвать native-метод на непустом `s.col`» уже
  используется `Flush`, `Query` и `Fetch`. Guard, который не детектирует условие, даёт
  ложную защиту; корректное решение — отдельный признак жизни handle, что выходит за
  рамки плана и затрагивает все вызовы, а не только новый.
- **`Failed: len(requested)` при сбое проверочного `Fetch`.** Ревьюер предлагает
  отдельный тип «unresolved». План требует «не трактовать ошибку Fetch как успех и не
  выдумывать точные per-ID результаты»; текущая форма это выполняет — `Succeeded`
  пуст, ошибка обёрнута, `errors.Is` работает. Отдельный тип — расширение публичного
  API, которое план запрещает («новые публичные API не требуются»).

### Ограничения

- Восстановление уже раздутого индекса — только `reindex` с `force: true`: новая
  staging-коллекция получает периодическую и финальную компакцию. Это требует
  пересчёта embeddings и места под staging, поэтому автоматически не запускается.
- Unchanged-прогон **не** освобождает место старого индекса: `dirty` знает только о
  записях через этот процесс, историческое раздувание он не обнаруживает.
- Отдельный публичный maintenance-tool в рамках плана не добавлялся.
- Ссылка `zvec-index-growth.md` в разделе «Основание» указывает на описание другого
  проекта, которого нет в этом репозитории; она сохранена как есть, поскольку план
  запрещает перезаписывать исходное описание.
