# Обновление zvec-go с v0.7.0 до v0.8.0

> **Для исполнителя:** использовать навык `executing-plans` либо `subagent-driven-development` и выполнять задачи с проверкой результатов. Этот документ сохранён по просьбе пользователя; разрешение на реализацию ещё не получено.

**Цель:** обновить Go-обвязку и соответствующие native-библиотеки до v0.8.0, сохранив поиск, индексацию, Windows Unicode-пути и режимы daemon/proxy.

**Архитектура:** сохранить локальный replace на `.deps/zvec-go` и существующий ACP-патч. Согласованно обновить pins и native-компоненты, не меняя схему поиска. Существующая политика миграции приложения потребует перестройки индексов.

**Стек:** Go, CGO, zvec-go v0.8.0, native zvec C API, PowerShell/Bash, Docker; production tags `zvec,onnx,treesitter`.

**Основание:** запрос пользователя подробно описать обновление zvec-go на последнюю версию; исследование репозитория и upstream от 21 октября 2026 года.

## Текущее состояние и источники

На момент проверки 21 октября 2026 года последний стабильный релиз Go-модуля — [zvec-go v0.8.0](https://github.com/zvec-ai/zvec-go/releases/tag/v0.8.0), опубликованный в 06:51 МСК. Версия самого MCP-сервера имеет отдельную нумерацию.

В репозитории:
- `go.mod` требует `github.com/zvec-ai/zvec-go v0.7.0`, но `replace` направляет сборку в `.deps/zvec-go`.
- Локальная зависимость находится на теге v0.7.0; поверх него применён ACP-патч Windows-путей.
- `internal/version/version.go` содержит `ZvecGoVersion = "v0.7.0"`.
- При исследовании рабочее дерево основного репозитория было чистым. В зависимости были ожидаемые изменения ACP-патча и дополнительные файлы.

Обновление не выполнялось. Сборка и тесты совместимости с v0.8.0 не запускались. MCP-инструменты `index_status` и `semantic_search` в сессии исследования были недоступны; использовалось точечное чтение исходников и GitHub upstream. Перед реализацией повторно проверить состояние дерева и доступность MCP.

Источники:
- [GitHub Release v0.8.0](https://github.com/zvec-ai/zvec-go/releases/tag/v0.8.0).
- [Сравнение v0.7.0 → v0.8.0](https://github.com/zvec-ai/zvec-go/compare/v0.7.0...v0.8.0).
- [Upstream go.mod](https://github.com/zvec-ai/zvec-go/blob/v0.8.0/go.mod).
- [Upstream collection.go](https://github.com/zvec-ai/zvec-go/blob/v0.8.0/collection.go).
- Локальные `docs/DEVELOPMENT.md`, `internal/store/zvec/migrate.go`, `internal/service/phase1.go`.

## Глобальные ограничения

- Сохранить MCP tools, HTTP API, аргументы и ответы.
- Сохранить интерфейс Store, dimensions, профили и chunking.
- Сохранить FP32 + HNSW + cosine, M=16, efConstruction=200 (`internal/store/zvec/schema.go`).
- Сохранить production tags `zvec,onnx,treesitter`.
- Сохранить расположение индексов, collection_id, registry, настройки и секреты.
- Сохранить ACP-патч и существующее управление mmap для Windows Unicode-путей.
- Не обновлять попутно остальные зависимости или версию MCP-сервера.
- Не внедрять UINT8, FTS/Jieba, новые ANN-индексы, PureGo, Alpine и расширение release matrix в рамках этого bump.
- Миграционные и smoke-проверки выполнять только на временных индексах.
- Не перезаписывать пользовательские изменения в основном репозитории и локальной зависимости.

## Что изменилось в v0.8.0

| Изменение upstream | Значение для проекта |
|---|---|
| Обновлён native core zvec | DLL/SO/DYLIB, C-заголовки и Go-исходники должны обновляться вместе |
| Удалены ConfigData.SetJiebaDictDir/GetJiebaDictDir и SetDefaultJiebaDictDir/GetDefaultJiebaDictDir | В проверенном коде internal вызовы отсутствуют; прямых правок приложения по этой причине не ожидается |
| Словари Jieba встроены в C-API библиотеку | Отдельные файлы словарей больше не нужны; custom dictionary остаётся доступен через per-field jieba_dict_dir или ZVEC_JIEBA_DICT_DIR |
| Добавлен DataTypeVectorUint8 | Не переводит наш FP32-поиск на UINT8 автоматически |
| PureGo-загрузчик требует ABI 0.8 | Не меняет наш CGO-режим, но подчёркивает необходимость согласованных native-компонентов |
| Linux prebuilts с baseline glibc 2.28; добавлены musl x64/ARM64 | Расширяет возможности upstream; не требует перевода Docker на Alpine |
| Добавлены macOS Intel и Windows ARM64 prebuilts | Не означает автоматическую поддержку этих платформ нашим продуктом: fetch/install/CI имеют свои ограничения |

Нюанс: стабильный тег Go-обвязки v0.8.0 указывает на native submodule commit `8397071d815cd842be2068339e00a94e69f069d1`, описанный в upstream-истории как v0.8.0-beta2. Не утверждать, что каждый внутренний компонент релиза имеет отдельный стабильный тег v0.8.0.

Не обещать автоматическое ускорение, уменьшение RAM или улучшение relevance: для текущего HNSW/FP32-сценария проверенные материалы таких гарантий не дают.

## Основные риски для ревью

1. Смешение новой Go-обвязки со старой DLL/SO из каталога запуска или PATH: проверить фактический runtime-комплект и штатный запуск.
2. Потеря локальных изменений зависимости из-за checkout -f/git clean: перед fetch сохранить любые изменения сверх воспроизводимого ACP-патча.
3. Регрессия Windows Unicode-путей: проверить применение ACP-патча и интеграционный Cyrillic-path сценарий.
4. Повторный сброс индекса при каждом открытии: проверить метаданные после rebuild и повторное открытие без миграции.
5. Global install затрагивает несколько коллекций: проверить изоляцию, восстановление каждой коллекции и режим без auto-index.

## Задача 1. Согласовать версии, локальную зависимость и native-комплект

**Изменяемые файлы:**
- `go.mod` — require v0.8.0, сохранить replace.
- `internal/version/version.go` — ZvecGoVersion v0.8.0.
- `scripts/fetch/fetch-zvec-libs.ps1` — default tag и комментарий.
- `scripts/fetch/fetch-zvec-libs.sh` — default tag и комментарий.
- `docker/Dockerfile` — ARG ZVEC_GO_TAG=v0.8.0.
- `go.sum` — только если изменится в результате необходимой обработки module graph.
- `scripts/fetch/patches/zvec-go-acp/collection.go.patch` — только если проверка покажет необходимость адаптации.

**Интерфейсы:** существующие fetch-скрипты, env ZVEC_GO_TAG, локальный replace и production tags остаются прежними. Результат задачи — воспроизводимая production-сборка с обвязкой и native libs одного релиза.

- [ ] Проверить git status основного репозитория и `.deps/zvec-go`; сохранить пользовательские изменения зависимости сверх ACP-патча. Fetch использует checkout -f и git clean.
- [ ] Проверить все пять pins: до изменений они должны показывать v0.7.0, после — v0.8.0. Не менять исторические упоминания старых версий.
- [ ] Обновить пять источников версии, сохранив replace и остальные зависимости.
- [ ] Запустить существующий fetch-процесс по новому тегу. Windows: `./scripts/fetch/fetch-zvec-libs.ps1`; POSIX: `bash scripts/fetch/fetch-zvec-libs.sh`.
- [ ] Проверить точный тег checkout v0.8.0, применение cStringPath в CreateAndOpen/Open и наличие соответствующих C-заголовков/native libs.
- [ ] Проверить маркер native-версии v0.8.0 и отсутствие старой перекрывающей библиотеки в каталоге запуска.
- [ ] Сверить скачанный release-архив с опубликованным upstream `.sha256`. Локальный hash native-файла в fetch контролирует кэш, но не заменяет проверку архива по опубликованному checksum. Большой рефакторинг загрузчика сюда не включать.
- [ ] Проверить module graph и при необходимости выполнить go mod tidy; изучить diff, исключив несвязанные обновления.
- [ ] Собрать production-бинарник: Windows `./scripts/dev/build-zvec-windows.ps1`, POSIX `make build-zvec`. Ожидается успешная сборка с tags zvec,onnx,treesitter.
- [ ] Проверить запуск production-бинарника с `--version` и отсутствие ошибок native linkage.
- [ ] После проверки сформировать отдельный коммит с русским сообщением, если пользователь разрешил коммиты.

Upstream collection.go не входит в diff v0.7.0...v0.8.0 и всё ещё использует C.CString(path). Текущий ACP-патч предположительно применим без переработки, но это необходимо подтвердить применением и тестами. Не удалять патч только из-за обновления зависимости.

## Задача 2. Подтвердить миграцию индексов и регрессионную совместимость

**Файлы:**
- `internal/store/zvec/migrate_test.go` — добавить явный сценарий v0.7.0 → v0.8.0, при необходимости используя существующие helpers.
- `internal/store/zvec/store_integration_test.go` и `store_cyrillic_integration_test.go` — существующие native gates; расширять только при отсутствии нужного покрытия.
- `internal/service/phase1.go` и существующие сервисные тесты — сохранить поведение миграции; добавлять точечные тесты auto-index/no-auto-index при недостаточном покрытии.
- `scripts/smoke/run-global-daemon.ps1` / `.sh` и существующий driver — использовать для multi-project gate.

**Интерфейсы:** существующие NeedsZvecGoMigration, ResetIndexForZvecMigration, MCP reindex(force=true). Результат — подтверждённое однократное восстановление индекса после bump без изменения пользовательского API.

### Поведение, которое нужно сохранить

`открытие коллекции → сравнение версии → сброс старого индекса → новое построение embeddings/чанков → поиск по новому индексу`.

Любое расхождение сохранённого zvec_go_version с версией бинарника вызывает миграцию. Сброс удаляет данные zvec-коллекции, очищает manifest и записывает полную identity metadata. Это политика приложения, а не установленный факт несовместимости on-disk формата upstream.

- Native с AUTO_INDEX_ON_START=true: миграция запускает force reindex.
- Global install: действует отдельный auto_index_on_open, по умолчанию включённый; проверить восстановление каждой коллекции при открытии.
- Legacy shared daemon без auto-index: ручной reindex(force=true) для каждой коллекции.

### Шаги проверки

- [ ] Добавить тесты с метаданными v0.7.0 и целевой v0.8.0: миграция необходима; reset очищает старые данные/manifest и сохраняет полную identity; повторная проверка после записи v0.8.0 не требует миграции; ошибка очистки возвращается вызывающему коду.
- [ ] Выполнить тесты миграции до изменений тестируемой логики. Если проверяется уже поддерживаемое поведение, ожидается PASS, а не искусственно созданный FAIL. При обнаружении дефекта сначала закрепить его падающим тестом.
- [ ] Проверить rebuild на временном индексе: после reindex metadata содержит v0.8.0, поиск возвращает контрольный документ, повторное открытие не сбрасывает индекс.
- [ ] Проверить Native auto-index и сценарий без auto-index: автоматическое восстановление либо явная необходимость reindex соответственно.
- [ ] Выполнить `go test ./...` и `go vet ./...`. На Windows при документированной EDR-проблеме допустим локальный non-PIE test-link workaround из docs/DEVELOPMENT.md; CI не менять.
- [ ] На Windows amd64 и Linux amd64 выполнить `go test -tags "integration,zvec" ./internal/store/zvec/...` с настроенным PATH/LD_LIBRARY_PATH. Ожидается PASS: create, insert, top-k, delete, close/reopen, read-only и Cyrillic-path сценарии.
- [ ] Проверить тесты ACP-патча в локальной зависимости и Windows Unicode-пути с новой DLL.
- [ ] Выполнить `go test -tags "zvec,treesitter" ./internal/indexer/chunk/...` с CGO и необходимыми native libs.
- [ ] Запустить phase1/phase2 smoke: Windows `./scripts/smoke/run-phase1.ps1`, `./scripts/smoke/run-phase2.ps1`; POSIX соответствующие .sh/Makefile targets. Ожидается успешное индексирование, поиск и path filter.
- [ ] Запустить global-daemon smoke с production-бинарником: Windows `./scripts/smoke/run-global-daemon.ps1`; POSIX `bash scripts/smoke/run-global-daemon.sh --binary ./bin/mcp-semantic-search-zvec-go`. Ожидается изоляция коллекций, работа proxy и повторное открытие после рестарта.
- [ ] Зафиксировать фактические команды и результаты. Если Linux-прогон отсутствует, отметить его как непроверенный gate, не объявлять обновление полностью квалифицированным.
- [ ] После проверки сформировать отдельный коммит тестов, если пользователь разрешил коммиты.

- `CHANGELOG.md` — новая запись об обновлении и последствиях для индексов.

**Интерфейсы:** существующие install-скрипты и управление daemon; формат конфигов и MCP API не меняется.

- [ ] Обновить текущие инструкции, не переписывая исторические записи о прежних релизах и старые планы.
- [ ] Явно описать однократную перестройку каждой затронутой коллекции, время и повторные embeddings-запросы. Для платного внешнего провайдера возможны расходы.
- [ ] Описать согласованный rollback: старый бинарник + native libs + backup индекса, снятый после штатной остановки. Один откат exe не возвращает старый индекс: старый бинарник также обнаружит расхождение версии metadata.
- [ ] Просмотреть итоговый diff: пять pins согласованы; API, schema, dimensions, chunking и остальные зависимости не изменены; секреты не затронуты.
- [ ] Зафиксировать документацию отдельным коммитом, если пользователь разрешил коммиты.

## Порядок развёртывания после успешных gates

1. Закрыть MCP-сессии, штатно остановить daemon и сделать согласованную резервную копию индексов.
2. Повторить install из обновлённого клона. Global install обновляет одно приложение для всех проектов.
3. Если Windows держит exe открытым, закрыть оставшиеся proxy-сессии и повторить install; не выполнять force kill.
4. Перезапустить IDE/daemon.
5. Открыть каждый проект и дождаться переиндексации; при необходимости вызвать MCP reindex с force=true.
6. Проверить index_status, отсутствие ошибок native linkage/LOCK и результаты контрольного semantic_search. Пока индексация выполняется, результаты могут быть пустыми или неполными.
